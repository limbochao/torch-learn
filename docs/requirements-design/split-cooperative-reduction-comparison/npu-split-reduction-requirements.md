# NPU Split Reduction 适配需求规格（PyTorch 2.13）

状态：需求规格草案，待评审。更新日期：2026-11-25。

当前开发实现见 [NPU Split Reduction 当前实现方案](npu-split-reduction-design.md)，
数据采集与阈值验证见 [测试脚本说明](../../../scripts/tests/npu_split_calibration/README.md)。
本稿记录目标能力与原始检查基线，首期建议范围不等于当前实现的自动准入范围；实现状态以方案文档为准。

**已决策事项：NPU 需要适配 split reduction。** 本文定义交付能力、适用边界与验收方式。
首期范围、硬件与编译模式、性能门槛为本稿建议，评审冻结后形成版本承诺。
算法、代码落点及参数搜索方法由方案设计确定；已有原型结果作为需求依据，不作为适配完成的证据。

## 1. 需求概述

在 NPU 的 `torch.compile` / Inductor 归约编译链路中提供 split reduction 能力。
对输出方向并行度不足、归约工作量较大的受支持计算，将同一输出的归约任务沿归约轴拆分，
由多个 program 计算局部结果，再通过后续 kernel 合并得到完整结果。
编译器应根据合法性和收益选择拆分策略，保持算子语义、数值精度及原有编译执行兼容性。
不适合拆分或尚未支持的场景应继续使用既有合法路径。

用户保持原有 PyTorch 算子和模型代码，无须手动切分张量、分配 partial 或启动合并 kernel。
交付对象是实际编译链路中的自动优化能力，验收包括生成代码、运行结果和完整计算的性能。

| 术语 | 本文含义 |
| --- | --- |
| `X` | 独立归约结果的数量，即非归约维度的元素数之积 |
| `R` | 每个归约结果对应的输入元素数，即归约维度的元素数之积 |
| `S` | 同一归约结果的分片数；`S=1` 表示不拆分 |
| partial / workspace | 局部归约状态，以及存放该状态的临时设备内存 |
| program / 物理核 | 前者为逻辑执行单元；两者不按一一对应关系解释 |
| 完整计算 | 从同一输入得到约定全部输出所需的所有设备操作，包含 partial、合并和后续消费者 |

## 2. 背景与现状依据

小输出、长归约轴计算可能只能沿输出方向生成少量任务，归约轴上的工作集中在少量 program 内。
Split reduction 的目标是在这些负载中增加归约方向并行度，其额外代价包括中间结果存取、
合并和 kernel 边界。是否获益需要对完整计算进行测量。

现有 [GPU/NPU 对照报告](results.md)包含 199 组共用 eager forward。
NPU 测量包括原生编译基线和手写 SIMD DSL 原型。部分代表结果如下，单位为 µs：

| 用例，fp32 连续输入 | 关闭 split/cooperative 的编译基线 | NPU split 原型 |
| --- | ---: | ---: |
| sum，`X=1, R=256` | 0.584 | 1.494 |
| sum，`X=1, R=262144` | 18.283 | 4.698 |
| sum，`X=1, R=1048576` | 69.840 | 6.660 |
| sum，`X=56, R=1048576` | 286.223 | 298.031 |

这些结果支持同时建设拆分能力和自动选择能力。原型的输入、算法、搜索空间及测量条件有限，
不能据此承诺固定加速倍数、直接确定通用阈值，或将其视为集成后的收益。

截至本文对应的本地源码快照，需区分以下能力状态：

| 路径 | 源码事实或已有证据 | 对本需求的意义 |
| --- | --- | --- |
| 上游 PyTorch | `Reduction.num_splits()`、`create_multilayer*()` 及分片选择逻辑已存在 | 可以评估复用，但设备选择与资源模型需适配 |
| NPU 默认 Triton 路径 | 覆盖上游 `num_splits()`；当前 `numel_hint != 1` 返回不拆分，恰有一个动态归约轴的标量归约也返回不拆分 | 不是完全没有拆分入口；需明确扩展哪些场景并贯通后续链路 |
| NPU 实验后端 | `triton_experimental` 有受条件限制的 sum partial/combine 实现及独立开关 | 属于可复用的实现线索，源码存在不等于默认后端已验收 |
| NPU 性能实验 | DSL split 原型已有运行与 profiler 对照 | 用于建立候选和反例，不能替代产品路径验收 |

源码快照与检查入口见第 10 节。本文未执行新的 NPU 运行测试。

## 3. 交付范围

### 3.1 首期建议范围

建议以 PyTorch 2.13、NPU 默认 Inductor → Triton-Ascend → 设备编译器链路为首期入口。
硬件验证优先沿用已有 Ascend950PR / NPU_A5 环境；具体 SoC、有效 Vector 核数、
软件版本和 compile mode 须在评审中冻结。其他硬件或模式保持既有行为，验证后再扩展支持声明。

| 维度 | P0：首期建议承诺 | P1：后续扩展建议 |
| --- | --- | --- |
| 归约类型 | `sum`、`mean`、`amax`、`amin`，仅值输出 | `prod`、布尔、带 index 归约、Welford 等复合状态，逐类定义合并语义 |
| 输入与输出 dtype | fp32、fp16、bf16 的原生算子语义，包含合法的显式 dtype 转换 | 更多整数、浮点和复合 dtype |
| 形状 | 静态 shape；连续输入的末轴归约和全量归约；支持非整除尾块 | 非末轴、多轴和复杂 stride 的性能优化 |
| 融合 | 归约前逐元素计算、最终归约值上的逐元素计算；不支持融合时允许合法拆开执行 | RMSNorm、softmax、归约值广播回整行、多轮依赖归约的专项优化 |
| 动态 shape | 与现有能力兼容；未提供拆分实现时走既有路径，不引入新的失败 | 动态 `X` / `R` 的拆分、分组调优与缓存复用 |
| 执行场景 | 普通调用、重复调用、缓存命中、受支持的 Graph capture/replay；训练图正确性回归 | C++ wrapper、AOT 等独立交付形态的专项适配 |
| 非连续输入等未优化组合 | 保持原有支持和错误语义，允许回退 | 在独立精度与性能证据基础上扩展拆分支持 |

P0 中每一项均须在指定硬件和模式下验收。若需缩小首期范围，应在规格评审时修改支持矩阵，
不能在验收时将承诺支持项改记为 SKIP。训练图中的每一个归约节点按自身支持条件选择策略。

### 3.2 范围边界

- 不新增用户侧 ATen 算子或要求修改模型表达式。
- Cooperative reduction、split 与 cooperative 的分层组合单独立项，不作为本需求完成条件。
- 不将 split scan、matmul split-K 或一般张量 `split` 的能力合并到本需求。
- 不要求所有归约均拆分，也不预先固定分片数、两阶段以外的实现形式或具体代码改造位置。
- P1 组合在本期须满足兼容要求，性能优化待扩展范围验收后再声明。

## 4. 功能要求

以下编号用于关联实现、用例和验收记录。

| 编号 | 要求 | 验收观察点 |
| --- | --- | --- |
| FR-01 自动接入 | 原始 PyTorch 图通过约定编译入口即可使用拆分；受支持且被选中的用例实际由多个 program 分担同一输出的归约，并完成合并 | 原图、编译 IR/生成代码、实际执行 kernel 序列与结果对应 |
| FR-02 完整语义 | 保持输出 shape、dtype、`dim`、负轴、`keepdim` 和合法 dtype 参数语义；每个有效元素恰好计入一次，尾块及空分片正确处理 | 与同语义 eager 和数值参考比较；覆盖不规则 `R` |
| FR-03 合并正确 | 按归约类型合并状态；归约前计算作用于原始元素，归约后计算作用于完整结果；不能重复执行非线性或带常数的 epilogue | 验证 `(a+b).sum(-1)`、`sum*0.5+1`、非等长分片的 mean |
| FR-04 自动选择 | 统一检查算子、dtype、布局、shape、资源与实现合法性，再判断收益；保留不拆分选项，支持多于一个输出的归约 | 自动模式覆盖明确获益、明确退化及边界用例；记录实际策略 |
| FR-05 开关与回退 | 提供关闭、自动及测试强制选择的控制语义；测试强制只能越过收益判断，不能越过合法性检查；关闭或不支持时使用既有合法路径 | 同图开关对照；`fullgraph=True` 场景不因本优化新增 graph break |
| FR-06 分片与资源 | 分片和局部 tile 适应实际可用资源，正确支持多 wave 调度；不套用 cooperative 的单 wave 参与限制 | 合法用例覆盖任务数小于、等于和大于有效核数；无越界、挂起 |
| FR-07 临时空间 | 编译器/runtime 管理 workspace 的大小、对齐、生命周期与依赖；写后读顺序正确，多调用、多 stream 和 Graph replay 不串用数据 | 变化输入、并发、缓存、Graph 及内存稳定性检查 |
| FR-08 动态兼容 | 动态参数参与分片、索引和 workspace 时须有正确运行时表达式或有效 guard；代表值不能直接当作运行时边界 | 跨多个 `X/R` 连续调用；不支持拆分时仍保持原有正确执行 |
| FR-09 融合兼容 | 保持计算依赖和结果消费者完整；多个归约、共享输入或多个输出不能漏算、错序或错误复用 partial | 同时返回 sum/amax、共享归约结果、多消费者及训练图回归 |
| FR-10 调优与缓存 | 调优候选满足合法性；选中策略、设备相关配置和 workspace 契约一致；影响生成结果的配置进入缓存区分条件 | 冷启动、热缓存、新进程恢复及开关变化后的执行一致性 |
| FR-11 可诊断 | 调试信息可识别普通/拆分路径、分片数、局部配置、模式、workspace 字节数及未选择原因 | 从一次用例的证据追溯选择与实际执行；不要求默认输出大量日志 |
| FR-12 失败处理 | 不支持和预计资源超限应在提交设备执行前排除；候选编译失败按既有机制处理，不吞掉设备异步错误并盲目重试 | 不支持组合、资源边界和候选失败的定向测试 |

上述控制语义优先复用现有配置体系。是否新增 NPU 专有配置项、测试 hook 或调试接口由设计说明，
需要明确与上游 `split_reductions` 及 cooperative 开关的优先关系，避免开关已开但执行路径含混。

### 4.1 语义验收示例

```python
def f(a, b):
    return (a + b).sum(dim=-1) * 0.5 + 1
```

例如输入为连续 fp32 的 `(7, 1048576)` 时，存在 7 个独立归约结果。
测试选择合法的 `S>1` 后，各分片处理对应行的一部分 `a+b`，合并得到该行的完整和，
最后对完整和执行 `*0.5+1`。这里不预设实际分片数或要求在某一固定 kernel 中执行 epilogue。

当 `R` 不能被分片数或 tile 整除时，padding 不得参与有效元素计数。
对 mean 应按总有效元素数合并，不能直接平均非等长分片的局部均值。

## 5. 精度与兼容要求

1. **原生 dtype 语义。** fp16/bf16 输入按算子约定进行累加、partial 存储和最终转换，
   不因跨 kernel 存储而引入额外的低精度舍入。显式 `dtype=` 必须生效。
   现有实验先将输入转为 fp32，不能替代原生低精度输出场景的验收。
2. **归约次序与误差。** 浮点归约拆分会改变计算次序，不以逐 bit 等于 eager 作为 sum/mean 的统一要求。
   算子×输入 dtype×输出 dtype 的 `rtol/atol`、参考算法及特殊值判定须在测试前冻结，
   不得为了使失败用例通过而逐点放宽。
3. **参考计算。** 与同图 NPU eager 比较，并在可行时增加高精度参考。
   融合前置计算的 dtype 和舍入位置需与原图一致，不能用不同的前置计算定义改变参考问题。
4. **特殊值。** 覆盖 0、正负数抵消、大动态范围、NaN、±Inf、极值相等及带符号零。
   `amax/amin` 的 NaN 与零符号行为按框架契约和冻结的比较规则检查，不能仅比较有限值误差。
5. **边界语义。** `X=0`、`R=0/1`、空张量和不合法参数遵守既有算子行为，包括应有的报错。
   不适合拆分的边界可以使用既有路径。
6. **运行一致性。** 遵守已有确定性模式契约；覆盖变化输入、连续调用、训练前后向和 Graph replay。
   精度或状态检查失败的候选不得进入有效性能结果。

## 6. 性能与成本要求

### 6.1 比较对象与指标

| 对象或指标 | 定义与用途 |
| --- | --- |
| B0：适配前产品基线 | 冻结版本的实际 NPU 编译路径，保留其既有优化和合法回退；作为产品收益及回归的主对照 |
| Bplain：诊断基线 | 明确关闭 split/cooperative 的编译路径，用于分析拆分本身的作用；不能取代 B0 |
| Bsplit / Bauto | 集成后的合法强制拆分路径与产品自动选择路径；前者验证能力，后者验证最终用户收益 |
| 完整 device 耗时 | 同一输入到全部输出所需设备操作 duration 之和，包含全部 partial、合并、必要初始化及消费者 |
| 完整调用/模型耗时 | 按生产调用方式测量同步完成的延迟或吞吐，包含运行时和 kernel 间开销；与 device 指标分别报告 |
| 编译与内存成本 | 首编译、调优时间、候选数、缓存命中/恢复时间、额外 workspace 及峰值设备内存 |

不能仅用第一阶段 kernel 的时间、较少的 kernel 数或相对手写原型的速度作为验收结论。
Graph 与非 Graph 模式分别记录和比较；热运行性能不包含编译、调优和预热时间。

### 6.2 验收集合与建议门槛

性能集合须在调优前冻结，包含目标收益集、退化控制集及模型回归集。
目标收益集按真实需求或既有原型证据预先列出，不能在得到结果后仅保留加速用例。
控制集至少覆盖小 `R`、输出并行度充分、非连续输入、不规则尾块和未支持组合。

下表给出可讨论的数值起点，**均为评审建议，不是现有实测结论或已经确认的交付承诺**：

| 编号 | 门槛建议 | 判定说明 |
| --- | --- | --- |
| PR-01 目标收益 | 目标集 B0/Bauto 加速比几何均值 ≥ 1.20 | 同图同输入、同设备和运行条件；同时报告每例结果及未达标点 |
| PR-02 选择质量 | Bauto 在冻结的普通/拆分候选中，无稳定超过 `max(较优候选耗时的 5%, 0.5 µs)` 的额外耗时 | 用完整 device 耗时判断，检查固定阈值是否漏选或误选 |
| PR-03 控制集回归 | Bauto 相对 B0 无稳定超过 `max(B0 耗时的 5%, 0.5 µs)` 的退化 | 全量保留控制集，短用例采用绝对与相对联合预算 |
| PR-04 模型回归 | 冻结模型集无稳定超过 1% 的端到端退化 | 需先确认环境能够分辨该幅度；实际收益依归约占比单独报告 |
| PR-05 工程成本 | 候选数、首编译/调优增量、workspace 和峰值内存不超冻结预算 | 现有证据不足以给出通用数值，评审须按平台和场景填写上限 |

PR-01 的聚合提升不能豁免 PR-02/03 的逐例回归检查。
若环境噪声大于门槛，应改善测量或在评审中重定可分辨门槛，不能将不稳定结果直接判为通过。

### 6.3 测量与选型约束

- 合法性检查独立于收益判断；自动选择至少考虑实际任务并行度、`R`、dtype、stride、
  融合形态、局部资源和合并成本。具体使用静态规则、成本模型或调优由方案决定。
- 使用实际有效核数及资源限制，不固定复用 GPU 的 SM/warp 常量或某张 NPU 的核数。
  `X` 仅是并行度线索，不能单独代替实际输出 tile 和任务数。
- 至少执行 3 个独立测量会话，预热后交替策略顺序，报告各会话统计与波动。
  测量方案预先明确重复次数、稳定性判据和复测规则，全部候选用同一口径。
- 对性能结论保留实际选中配置和 profiler 操作序列；模型收益使用单独的端到端测量。
  原始日志、IR、trace 和缓存放在项目外，仓库保留最终结果、脚本及说明。

## 8. 依赖与交付件

| 领域 | 需要明确的责任或产出 |
| --- | --- |
| Inductor | 准入与选择、IR/调度/代码生成、workspace 规划、融合依赖及回退一致性 |
| NPU runtime | 有效设备资源查询、kernel 顺序与 stream 依赖、临时空间生命周期、Graph 和缓存契约 |
| Triton-Ascend / 设备编译器 | 声明模式下各阶段归约、mask、dtype 转换和局部资源使用的编译执行支持 |
| 测试与性能 | 冻结功能矩阵、数值规则、性能集合、测量方法、设备环境和结果证据 |

基础 split 路径依赖 kernel 之间的执行依赖来传递 partial，不以同一 kernel 内的跨 program
全局 barrier、cooperative launch 或所有分片同时驻留作为必需能力。
实现若引入其他同步机制，应在设计中单独说明其必要性和契约。

交付件包括：本规格及冻结记录、方案设计与支持矩阵、产品路径实现、功能与回归用例、
可复现性能脚本及报告、精度与资源成本报告、配置和未支持项说明。
支持矩阵至少按 SoC×软件版本×compile mode×算子×dtype×布局×静态/动态标明状态，
区分源码实现、编译通过、运行通过和达到性能门槛。

## 9. 评审冻结项与完成条件

下列决策关系到交付边界，需在规格评审时落实；无需重新论证是否建设 split reduction：

| 冻结项 | 本稿建议或当前状态 |
| --- | --- |
| 首期后端与版本 | PyTorch 2.13 NPU 默认 Triton 路径；实验后端成果按实际复用情况单独说明 |
| 首期硬件和 compile mode | 优先已有 Ascend950PR / NPU_A5；填写发布承诺的 SoC、核预算、模式及软件版本 |
| P0 算子/dtype/布局范围 | 建议采用第 3.1 节；范围调整在评审阶段完成 |
| 精度判据 | 按第 5 节冻结各算子和 dtype 的参考及误差规则 |
| 性能与模型集合 | 冻结 case 清单、模型名称/版本、输入与权重；现有矩阵为起点 |
| 性能数字与成本预算 | 评审 PR-01～05；为编译、调优、候选和 workspace 填写可执行上限 |
| 配置、默认启用和回退 | 明确现有开关映射及与 cooperative 的关系；按已验收平台分阶段启用 |

**完成条件：** 冻结范围内的 P0 功能和兼容用例全部通过；确认实际执行了拆分与合并；
精度满足预设规则；目标性能、控制集回归和工程成本满足冻结门槛；证据与版本可追溯。
SKIP、仅编译通过、手写原型通过或未达到稳定性要求的测量，不能代替承诺能力的验收。
